# Manifest Taxonomy

**doc_type: explanation**

For platform engineers and security officers who need to understand the three manifest types and their roles in the build-deploy lifecycle.

## Concept Summary

The build system uses three distinct manifests at different lifecycle stages. Each serves a specific purpose and audience. Confusion between them causes errors in configuration, validation, and deployment.

## The Three Manifests

### 1. Component Manifest (Input)

**File**: `config/components.yaml`
**Phase**: Pre-build (Zone A - connected environment)
**Purpose**: Declarative specification of what to collect
**Owner**: Platform engineer (manually edited)
**Format**: YAML (custom schema)

The component manifest is your shopping list. It declares what you want to collect: tools, repositories, images, charts. It uses templates and auto-discovery directives to keep it concise and maintainable.

**Characteristics**:
- Templates with `{{version}}` placeholders
- Auto-discovery directives (scan repos for images)
- No checksums (URLs not yet fetched)
- Human-readable, version-controlled
- Edited by platform engineers

**Example**:
```yaml
kubernetes:
  version: "1.34.3"
  binaries:
    - name: kubectl
      url: "https://dl.k8s.io/v{{version}}/bin/linux/amd64/kubectl"

repositories:
  - name: kubespray
    url: "https://github.com/kubernetes-sigs/kubespray.git"
    ref: "master"

images:
  auto_discover:
    - source: repositories.kubespray
      patterns:
        - "roles/*/defaults/main.yml"
```

### 2. Zarf Manifest (Build Instructions)

**File**: `zarf.yaml`
**Phase**: Build (Zone A - connected environment)
**Purpose**: Zarf package definition - how to collect and bundle
**Owner**: Generated by `opencenter-airgap generate-manifest`
**Format**: YAML (Zarf schema)

The Zarf manifest is the build recipe. It tells Zarf exactly how to collect artifacts, where to download them, and how to package them. It's generated from the component manifest with all templates resolved and discovery expanded.

**Characteristics**:
- Templates resolved (`{{version}}` → `1.34.3`)
- Auto-discovery expanded (115+ concrete image references)
- Zarf-native format (components, actions, variables)
- Generated, ephemeral (can be regenerated)
- Consumed by Zarf CLI

**Example**:
```yaml
kind: ZarfPackageConfig
metadata:
  name: opencenter-airgap
  version: 1.0.0

components:
  - name: images
    required: true
    images:
      - registry.k8s.io/kube-apiserver:v1.34.3
      - registry.k8s.io/kube-controller-manager:v1.34.3
      - quay.io/calico/node:v3.27.0
      # ... 112 more images

  - name: files
    required: true
    files:
      - source: build/kubespray-offline/outputs/files/kubectl
        target: /opt/opencenter/files/kubectl
```

### 3. Artifact Manifest (Output Inventory)

**Files**: `dist/artifact-manifest.json`, `dist/artifact-manifest.md`
**Phase**: Post-build (Zone A) / Pre-deploy (Zone B/C)
**Purpose**: Cryptographic inventory of what was actually collected
**Owner**: Generated by `opencenter-airgap build`
**Format**: JSON (machine-readable) + Markdown (human-readable)

The artifact manifest is the bill of materials. It's a cryptographic inventory of every artifact collected, with checksums, sizes, and resolved versions. Security officers use it to verify package integrity before deployment.

**Characteristics**:
- SHA256 checksums for every artifact
- Actual sizes (bytes collected)
- Resolved Git commit SHAs (not branch names)
- Image digests (immutable content-addressable IDs)
- Collection timestamps
- Immutable, signed (Cosign)

**Example** (JSON):
```json
{
  "build_id": "20260130-143022",
  "timestamp": "2026-01-30T14:30:22Z",
  "images": [
    {
      "name": "registry.k8s.io/kube-apiserver:v1.34.3",
      "digest": "sha256:a1b2c3d4...",
      "size": 134217728
    }
  ],
  "binaries": [
    {
      "name": "kubectl",
      "version": "1.34.3",
      "path": "/opt/opencenter/files/kubectl",
      "size": 45678901,
      "sha256": "e5f6g7h8..."
    }
  ],
  "repos": [
    {
      "url": "https://github.com/kubernetes-sigs/kubespray.git",
      "ref": "master",
      "commit_sha": "i9j0k1l2...",
      "size": 12345678
    }
  ],
  "total_artifacts": 247,
  "total_size": 8589934592
}
```

## Why Three Manifests?

Each manifest serves a distinct purpose at a different lifecycle stage:

**Component Manifest** (Input):
- Maintainable: Templates and auto-discovery keep it concise
- Version-controlled: Track changes to what you collect
- Human-readable: Platform engineers edit it directly

**Zarf Manifest** (Build Instructions):
- Zarf-native: Uses Zarf's schema and features
- Concrete: All templates resolved, all images listed
- Reproducible: Same manifest produces same package

**Artifact Manifest** (Output Inventory):
- Verifiable: Checksums prove integrity
- Auditable: Security officers verify before deploy
- Immutable: Signed, tamper-evident

## Lifecycle Flow

```
┌─────────────────────┐
│ Component Manifest  │  Platform engineer edits
│ components.yaml     │  (what to collect)
└──────────┬──────────┘
           │
           │ opencenter-airgap generate-manifest
           ▼
┌─────────────────────┐
│   Zarf Manifest     │  Generated from component manifest
│   zarf.yaml         │  (how to collect)
└──────────┬──────────┘
           │
           │ opencenter-airgap build
           │ (collects artifacts)
           ▼
┌─────────────────────┐
│ Artifact Manifest   │  Generated after collection
│ artifact-manifest.* │  (what was collected)
└─────────────────────┘
```

## Common Misconceptions

### "I can edit zarf.yaml directly"

You can, but don't. The Zarf manifest is generated from the component manifest. Manual edits to `zarf.yaml` are lost on the next `generate-manifest` run.

**Correct approach**: Edit `config/components.yaml`, then regenerate:
```bash
opencenter-airgap generate-manifest
```

### "The artifact manifest is just documentation"

No. It's a cryptographic inventory used for verification. Security officers compare it against the package to detect tampering:

```bash
opencenter-airgap verify dist/zarf-package-*.tar.zst \
  --manifest dist/artifact-manifest.json
```

### "I need to version-control all three manifests"

Only version-control the component manifest (`config/components.yaml`). The Zarf manifest and artifact manifest are generated artifacts.

**Version control**:
- ✅ `config/components.yaml`
- ❌ `zarf.yaml` (generated)
- ❌ `dist/artifact-manifest.json` (generated)

### "The manifests contain the same information"

They overlap but serve different purposes:

| Information | Component | Zarf | Artifact |
|-------------|-----------|------|----------|
| What to collect | ✅ | ✅ | ✅ |
| Version templates | ✅ | ❌ | ❌ |
| Auto-discovery | ✅ | ❌ | ❌ |
| Resolved versions | ❌ | ✅ | ✅ |
| Checksums | ❌ | ❌ | ✅ |
| Actual sizes | ❌ | ❌ | ✅ |
| Git commit SHAs | ❌ | ❌ | ✅ |
| Image digests | ❌ | ❌ | ✅ |

## Comparison Table

| Aspect | Component Manifest | Zarf Manifest | Artifact Manifest |
|--------|-------------------|---------------|-------------------|
| **File** | `config/components.yaml` | `zarf.yaml` | `dist/artifact-manifest.json` |
| **Format** | YAML (custom schema) | YAML (Zarf schema) | JSON |
| **Purpose** | Declare what to collect | Instruct Zarf how to build | Inventory what was collected |
| **Audience** | Platform engineer | Zarf CLI | Security officer, auditor |
| **Lifecycle** | Pre-build (input) | Build (instructions) | Post-build (output) |
| **Mutability** | Version-controlled, edited | Generated, ephemeral | Immutable, signed |
| **Hashes** | None | None | SHA256 for every artifact |
| **Git refs** | Branch names (`master`) | Branch names | Commit SHAs (`a1b2c3d4...`) |
| **Images** | Discovery directives | Full list (115 images) | Full list + digests |
| **Templates** | `{{version}}` | Resolved (`1.34.3`) | Resolved |
| **Size** | ~200 lines | ~2000 lines | ~5000 lines |

## When to Use Each

### Component Manifest

**Use when**:
- Adding new tools, repos, images, or charts
- Updating versions
- Configuring auto-discovery patterns
- Version-controlling build requirements

**Commands**:
```bash
opencenter-airgap add tool helm 3.14.0 https://...
opencenter-airgap add repo kubespray https://... master
opencenter-airgap validate
```

### Zarf Manifest

**Use when**:
- Debugging Zarf package creation
- Understanding what Zarf will collect
- Verifying template resolution
- Checking expanded image list

**Commands**:
```bash
opencenter-airgap generate-manifest
zarf package create --confirm
```

### Artifact Manifest

**Use when**:
- Verifying package integrity
- Auditing collected artifacts
- Comparing builds
- Detecting tampering

**Commands**:
```bash
opencenter-airgap verify dist/zarf-package-*.tar.zst \
  --manifest dist/artifact-manifest.json
```

## Trade-offs

### Why not a single manifest?

**Separation of concerns**:
- Component manifest: Human-editable, version-controlled
- Zarf manifest: Machine-generated, Zarf-native
- Artifact manifest: Cryptographic, immutable

Combining them would sacrifice maintainability (templates), compatibility (Zarf schema), or verifiability (checksums).

### Why generate Zarf manifest?

**Maintainability**: Component manifest with templates and auto-discovery is 10x smaller than expanded Zarf manifest.

**Example**:
- Component manifest: 200 lines
- Zarf manifest: 2000 lines (115 images × 1 line each + boilerplate)

Editing 2000 lines manually is error-prone. Generating from 200 lines is reliable.

### Why separate artifact manifest?

**Verification**: Artifact manifest is signed and used for integrity checks. Embedding it in the Zarf manifest would make it mutable and unverifiable.

**Auditability**: Security officers need a standalone inventory for compliance. Extracting it from the Zarf package is cumbersome.

## Summary

Three manifests, three purposes:

1. **Component Manifest**: What to collect (input)
2. **Zarf Manifest**: How to collect (instructions)
3. **Artifact Manifest**: What was collected (output)

Edit the component manifest. Generate the Zarf manifest. Verify with the artifact manifest.
